# Arquitectura del catálogo y Supabase

## Frontera de datos

`specs/products.json` es el fixture canónico y la fuente inicial. `CATALOG_SOURCE=json` es el valor por defecto y permite desarrollar, compilar y servir ambas aplicaciones sin red ni credenciales de Supabase. Cada servidor selecciona un lector al componer la página. En Next.js será un módulo de servidor tipado y en Laravel un servicio que el controlador recibe desde el contenedor. La única operación necesaria es listar el catálogo ordenado, con `Promise<readonly Product[]>` en TypeScript y una lista de DTO equivalentes en PHP. Blade y React reciben los mismos campos del [contrato funcional](behavior-contract.md#product-schema) y forman sus modelos de presentación sin conocer la fuente.

En la fase Supabase, `CATALOG_SOURCE=supabase` activa un adaptador que consulta la Data API de Supabase por HTTPS exclusivamente desde el servidor, con la clave publicable en `apikey` y `Accept-Profile: catalog`. Usar `fetch` y el cliente HTTP de Laravel. Solicitar en una consulta los productos y las relaciones de categoría, formato, autor y detalle, con columnas explícitas y orden `sort_order,id`. Conservar las filas padre al embeber las relaciones para detectar un detalle ausente durante la validación. Mapear el resultado al mismo DTO con campos en camelCase, etiquetas de formato, céntimos enteros, fecha `YYYY-MM-DD` sin zona horaria y nulos correspondientes a cada tipo. Validar los datos al entrar, sin exponer la forma de la base a los componentes. La página consulta en tiempo de petición, con timeout acotado y sin caché remota propia en la primera versión del adaptador. Mantener los filtros y la búsqueda en el navegador. [Data API con esquemas personalizados](https://supabase.com/docs/guides/api/using-custom-schemas) · [Claves de Supabase](https://supabase.com/docs/guides/getting-started/api-keys).

Una fuente remota inválida o indisponible muestra un estado de error en italiano y conserva los enlaces y el formulario de demostración. El error se registra sin valores de entorno ni detalles internos en el HTML. El estado vacío de búsqueda se reserva para consultas válidas. El retorno a `json` es un cambio explícito de configuración en ambos despliegues. El catálogo y los créditos son ficticios. El formulario no comparte este repositorio ni necesita tablas, endpoint o credenciales.

## Modelo relacional

Usar un esquema `catalog` con cinco tablas. Las columnas son `NOT NULL` salvo `age_range` y `start_date`, cuya nulabilidad depende del tipo. Los IDs de referencia son slugs estables. El campo `sort_order` replica el orden del JSON y sirve para ambos adaptadores.

| Tabla | Columnas y restricciones |
| --- | --- |
| `categories` | `id text` PK, `name text` único. Los IDs iniciales son `clinica`, `scuola`, `lavoro` y `formazione`. `Tutti` existe solo en la interfaz. |
| `formats` | `id text` PK, `name text` único. Slugs `digitale`, `cartaceo`, `corso-online` e `in-presenza` con las etiquetas del contrato de comportamiento. |
| `authors` | `id text` PK, `display_name text` obligatorio. Un producto tiene un crédito de autoría o docencia según `kind`. Los nombres visibles proceden del JSON y no incluyen datos de contacto. |
| `products` | `id text` PK, `name`, `description`, `image_path` obligatorios, `kind` con `CHECK` para `test` o `course`, `category_id`, `format_id`, `author_id` como FK obligatorias, `original_price_cents` y `discount_price_cents` enteros con `original > discount > 0`, `sort_order` entero no negativo y único, `is_published boolean default false`, y `UNIQUE (id, kind)` para la FK del detalle. |
| `product_details` | `(product_id, kind)` es PK y FK a `products(id, kind)` con borrado en cascada. `CHECK` exige `age_range` no nulo ni vacío y `start_date` nulo para test, o `start_date date` informado y `age_range` nulo para curso. Cada producto publicable requiere exactamente un detalle. |

Las relaciones categoría/formato/autor a producto son 1:N. Producto a detalle es 1:1 para publicaciones. La FK compuesta y el `CHECK` aseguran tipo y campos, y el seed transaccional junto con la validación de publicación aseguran la existencia del detalle. Publicar solo tras comprobar detalle y ruta de imagen. El adaptador considera inválida una fila publicada sin detalle. Los recursos gráficos siguen empaquetados con las aplicaciones.

## Migraciones y seeds

1. Cuando se implemente Supabase, versionar migraciones SQL bajo `supabase/migrations/` con prefijo temporal. Crear primero esquema, tablas y restricciones, y versionar la configuración de acceso y RLS. Aplicar cambios posteriores en migraciones nuevas. Supabase es propietario del esquema. Laravel y Next.js solo lo consumen. [Migraciones con Supabase CLI](https://supabase.com/docs/guides/deployment/database-migrations).
2. Generar un seed SQL determinista e idempotente desde `specs/products.json`, con mapeos estables para slugs de formatos, categorías y autores. Aplicar referencias, productos y detalles en una transacción, comprobar completitud y publicar las ocho filas con el orden de origen. Usar upserts por ID. La sincronización de bajas será explícita mediante despublicación. `supabase/seed.sql` sirve para el entorno local. El seed aprobado se aplica de forma explícita tras las migraciones del entorno de destino, nunca al arrancar o compilar una aplicación.
3. Antes de activar la fuente, probar el reset local, la aplicación de migraciones en limpio y la repetición del seed. Comparar todos los campos y el orden de los ocho DTO de Supabase con JSON. Comprobar producto no publicado, intento de escritura, referencias inválidas y timeout según los criterios del plan.

## RLS, permisos y configuración

- Exponer `catalog` en la configuración de Data API. Conceder `USAGE` de esquema y `SELECT` explícito en las cinco tablas a `anon`. Habilitar RLS en todas. En `products`, política de SELECT `USING (is_published)`. En `product_details`, SELECT solo si el producto padre está publicado. En las tres tablas de referencia, permitir la lectura de taxonomías y créditos ficticios, que son información pública. Verificar las relaciones embebidas ejecutando la consulta real como `anon`. Revocar privilegios heredados innecesarios y evitar permisos de escritura de `anon` o `authenticated`. Los usuarios finales leen el catálogo público sin sesión. [Control de acceso a la Data API](https://supabase.com/docs/guides/api/securing-your-api) · [RLS en Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security).
- `CATALOG_SOURCE` admite `json` o `supabase`. En modo `supabase` requerir `SUPABASE_URL` HTTPS y `SUPABASE_PUBLISHABLE_KEY` en ambos runtimes, con validación de configuración en servidor. Inyectarlas por entorno. A consume variables de servidor sin prefijo `NEXT_PUBLIC_`. B las lee a través de un archivo de configuración compatible con `config:cache`. Los `.env.example` futuros documentan nombres y valores de ejemplo. Las variables reales viven en local fuera de Git o en las plataformas. Aunque la clave publicable tiene privilegios de `anon`, las aplicaciones hacen sus solicitudes solo desde el servidor.
- Las credenciales de migración, contraseñas de PostgreSQL y claves privilegiadas se reservan al proceso administrativo de Supabase con acceso restringido. Las aplicaciones y sus builds no las necesitan. Probar accesos con la clave publicable, incluyendo lectura de un producto publicado, exclusión de borradores y rechazo de INSERT/UPDATE/DELETE, en la base de prueba autorizada.
